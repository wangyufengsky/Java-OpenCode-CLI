# Git 与单元测试链路领导简版 PPT 设计

## 沟通目标

汇报结束后，管理者应理解：本项目通过“执行、检查、反馈、再执行”的有界 Loop，让 Agent 能稳定完成 Git 贡献分析和单元测试生成等重复工程工作，并在可追溯、可验收的前提下减少人工投入。

## 受众与时长

- 受众：技术管理者、研发负责人、非一线开发领导。
- 时长：约 10 分钟。
- 页数：8 页。
- 阅读方式：可独立阅读，也适合现场讲解。

## 表达原则

- 先讲业务问题和管理价值，再解释技术机制。
- 不展示代码、长 Prompt、接口字段和复杂文件树。
- Loop 使用“提交、检查、退回修改、验收通过”的工作管理类比。
- 效率数字统一标记为“场景测算”，不得写成已验证的生产统计。
- 保留失败上限、人工接管和真实产物验收，避免把项目描述成无限自动化。

## 8 页结构

1. **项目一句话**：让 Agent 自动完成重复的软件工程工作。
2. **当前问题**：Git 贡献整理与单元测试补齐依赖人工，耗时、口径不一、过程难追溯。
3. **Loop 是什么**：执行一次不够，系统会执行、检查、反馈、再执行，直到通过或达到上限。
4. **项目能做什么**：统一接收任务、调用 Agent、检查真实产物、自动重试、记录全过程。
5. **Git 场景**：自动整理个人贡献与团队综合报告，缺失时只补跑未完成对象。
6. **单测场景**：按类生成测试，编译或执行失败后，根据真实错误继续修正。
7. **效率测算**：人工投入预计减少 60%–80%，同时展示假设与计算公式。
8. **管理价值与试点建议**：提效、标准化、可追溯、可控；建议从一个仓库和一个小包开始试点。

## 效率测算口径

使用可调整的场景模型，不引用未经验证的生产数据：

- Git 报告：人工整理、核对、汇总需要约 4 小时；系统执行后人工复核约 0.8–1.5 小时，人工投入减少约 63%–80%。
- 单元测试：人工分析、编写、运行和修正需要约 1.5 小时/类；系统执行后人工复核约 0.3–0.6 小时/类，人工投入减少约 60%–80%。
- 领导页统一展示为“预计减少 60%–80% 人工投入”，并注明结果受代码复杂度、历史测试基础和验收标准影响。

## 视觉设计

- 沿用现有 PPT 的蓝白主色与深蓝强调色，保持品牌连续性。
- 标题使用结论式表达；每页只保留一个核心观点。
- 使用少量大数字、简单箭头和对比图，不使用密集卡片和程序截图。
- Loop 页使用四步环形或闭环流程；效率页使用“传统方式 vs Loop 方式”的人工时间对比。

## 验收标准

- 恰好 8 页，顺序符合设计。
- 领导无需阅读原 30 页手册即可理解项目价值与 Loop。
- 不出现运行结果占位页、真实运行失败细节或未经验证的生产数据。
- “60%–80%”附近必须出现“场景测算”与假设说明。
- 最终 PPTX 逐页渲染，无文字截断、重叠或画布溢出。
